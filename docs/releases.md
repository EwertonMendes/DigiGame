# DigiGame release builds

DigiGame release packages are built entirely by GitHub Actions. A local Godot installation is not required to produce Windows, Linux, macOS, or Android packages.

The workflow is `.github/workflows/release.yml` and uses the same Godot baseline as the project CI: Godot 4.7.2.

## Version versus build attempt

A **version** identifies the game release, for example `0.1.0` or `0.1.0-rc.1`.

A **build attempt** is one execution of the GitHub Actions workflow.

They are intentionally independent. You can build `0.1.0` ten times while fixing packaging problems without creating ten versions. GitHub's run number identifies each build attempt, while the version remains `0.1.0`.

Accepted version formats:

- `0.1.0`
- `0.1.0-rc.1`
- `0.1.0-beta.2`
- `v0.1.0` (the leading `v` is accepted and normalized)

Use semantic `major.minor.patch` versions. Build metadata with `+` is intentionally not accepted so artifact names remain portable across all supported platforms.

## Build packages without publishing a release

Use this for development builds, QA, release candidates, and repeated attempts of the same version.

1. Open **Actions** in the GitHub repository.
2. Select **DigiGame Release Builds**.
3. Select **Run workflow**.
4. Select the branch you want to build. Normally use `master`; a feature branch can be used for test packages.
5. Enter the version in **Version to build**, for example `0.1.0`.
6. Leave **Publish these artifacts as a GitHub Release** disabled.
7. Run the workflow.
8. Open the completed run and download the artifacts.

You can repeat these steps with exactly the same version. Nothing is published and no Git tag is created.

Each run produces:

- `DigiGame-v<version>-Windows-x86_64.zip`
- `DigiGame-v<version>-Linux-x86_64.tar.gz`
- `DigiGame-v<version>-macOS-universal.zip`
- `DigiGame-v<version>-Android-arm64.apk`
- `SHA256SUMS.txt`
- `release-manifest.json`

Artifacts are kept by GitHub Actions for 30 days.

The manifest records the selected game version, Android version code, Godot version, source commit, source ref, workflow run ID, run number, and run attempt.

## Publish an official GitHub Release

Only publish after the exact same version has been tested successfully with normal build runs.

1. Make sure the code to release is merged into `master`.
2. Make sure persistent Android signing is configured as described below.
3. Open **Actions** > **DigiGame Release Builds**.
4. Select **Run workflow** and explicitly select the `master` branch.
5. Enter the desired version.
6. Enable **Publish these artifacts as a GitHub Release**.
7. Leave **Mark the GitHub Release as a prerelease** enabled for alpha, beta, RC, preview, or other non-final releases.
8. Disable the prerelease option only for a stable public release.
9. Run the workflow.

The workflow builds all four targets first. A GitHub Release is created only after every export and packaging step succeeds.

The release tag is generated as `v<version>`. For example, version `0.1.0` creates tag `v0.1.0`.

Release notes are generated by GitHub automatically.

### Published versions are immutable

A published version is treated as immutable. If `v0.1.0` has already been published, the workflow refuses to overwrite it.

If a code change is required after publishing `0.1.0`, create a new version such as `0.1.1`.

Before a version is published, you may run unlimited non-publishing builds using the same version.

If the publishing job itself is interrupted after it created a draft release, rerunning the same version from the same commit resumes that draft and replaces its incomplete assets. A fully published release is never silently replaced.

## Android signing

Normal non-publishing CI builds can produce an APK with an ephemeral CI key when Android signing secrets have not been configured. That APK is suitable for temporary testing, but a later APK created with another ephemeral key cannot update it in place.

Official GitHub Releases require a persistent Android signing key.

Generate the key **once**, back it up securely, and never commit it to the repository. Losing the production key can prevent future Android builds from updating an installed copy of the game.

A JDK `keytool` command can create the keystore:

```text
keytool -genkeypair -v -keystore digigame-release.keystore -alias digigame -keyalg RSA -keysize 2048 -validity 10000
```

Use the same password for the keystore and key. Godot currently expects the release keystore password and key password to match.

Create these repository Actions secrets under **Settings > Secrets and variables > Actions**:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64 representation of the complete keystore file |
| `ANDROID_KEYSTORE_ALIAS` | Key alias, for example `digigame` |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore/key password |

On Windows PowerShell, the Base64 value can be copied to the clipboard with:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("digigame-release.keystore")) | Set-Clipboard
```

The workflow reconstructs the keystore only inside the temporary GitHub runner and provides its path and credentials to Godot through the supported Android export environment variables.

Do not add `.keystore`, `.jks`, certificates, passwords, or Base64 signing material to the repository.

## Version metadata

The selected workflow version is not only used in filenames.

During the disposable CI checkout, `tools/prepare_release_metadata.py` applies release metadata before export:

- Android `version/name` receives the selected version.
- Android `version/code` receives the monotonically increasing GitHub Actions run number.
- Windows file/product versions receive the numeric `major.minor.patch.0` version.
- macOS short/build versions receive the numeric `major.minor.patch` version.
- Godot's project version receives the numeric `major.minor.patch` version.

For prerelease versions such as `0.1.0-rc.1`, package names and Android's visible version retain the full prerelease label, while platforms that only accept numeric version fields receive `0.1.0`.

These changes happen only inside the CI runner. Running a release build does not create a version-bump commit.

## Platform notes

### Windows

The workflow exports a 64-bit Windows executable with its PCK embedded and packages it as a ZIP.

Windows code signing is not configured yet. Windows may therefore show reputation or SmartScreen warnings for downloaded builds. Code signing can be added later without changing the version/build workflow.

### Linux

The workflow exports a 64-bit Linux executable with its PCK embedded and packages it as a `.tar.gz`.

### macOS

The workflow exports the official Godot Universal binary, supporting Intel and Apple Silicon, and packages the application as a ZIP.

Apple Developer signing and notarization are not configured yet. Gatekeeper may require users to explicitly allow an unsigned downloaded application. Signing/notarization can be added later without changing the version/build workflow.

### Android

The current target is an ARM64 APK suitable for sideloading on modern Android devices.

Google Play distribution should use an AAB with production signing. That can be added as a separate store-publishing stage later; it should not replace the APK used for direct testing.

## Automatic pipeline validation

Changes to the release workflow, export presets, release metadata helper, or this document trigger a non-publishing release build on pull requests to `master`.

The PR validation uses a synthetic version such as `0.0.0-pr.123`. It never creates a GitHub Release.

This keeps the release infrastructure testable without publishing fake versions.

## Release checklist

Before publishing a stable version:

- The intended commit is on `master`.
- Normal Web CI is green.
- A non-publishing multi-platform build for the intended version is green.
- Windows package was smoke-tested on Windows.
- Linux package was smoke-tested on Linux when practical.
- macOS package was smoke-tested on macOS when practical.
- Android APK was installed and launched on a device.
- Persistent Android signing secrets are configured.
- The version number is correct.
- **Prerelease** is set correctly.
- The published tag does not already exist.

After publishing, download at least one asset from the GitHub Release and verify its SHA-256 checksum against `SHA256SUMS.txt`.
